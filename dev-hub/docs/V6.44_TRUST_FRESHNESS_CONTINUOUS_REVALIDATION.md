# V6.44 — Trust Freshness & Continuous Revalidation

Status: IMPLEMENTATION / NOT ACQUIRED

## Goal

V6.43 established project-distinct trust graduation. V6.44 makes durable reuse freshness-aware without inventing a second clock or mutating historical trust.

The authoritative freshness source is the existing Technology Watch runtime:
- global snapshot maximum age: 60 minutes;
- background refresh: 30 minutes;
- targeted refresh when missing or stale;
- automatic external spend: 0 EUR.

## Contract

Immediately before durable capability merge, ChaCha DEV produces a capability trust freshness proof bound to the exact `capability + adoption_id`.

A proof is valid when:
- it is produced from Technology Watch consultation;
- the current snapshot is fresh OR a targeted refresh was performed;
- a source snapshot digest exists;
- automatic external spend is 0 EUR;
- every unlocked durable adoption is explicitly bound.

If the proof is missing, invalid or bound to another adoption, fast reuse is blocked before capability-gap detection.

Freshness does not rewrite V6.43 trust history. A historically TRUSTED capability remains historically TRUSTED, but is not active for fast reuse until current revalidation exists.

Negative trust always wins: DEGRADED, QUARANTINED and RECOVERY_CANDIDATE cannot be unlocked by a fresh Technology Watch proof.

## Preserved authority

- Technology Watch mandatory.
- Guardian preserved.
- Sentinel preserved.
- Architecture Council final.
- No production/network/secret permission is granted by trust freshness.
- Automatic external spend remains 0 EUR.
