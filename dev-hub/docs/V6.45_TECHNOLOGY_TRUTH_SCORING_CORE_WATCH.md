# V6.45 — Technology Truth Scoring & Core Architecture Watch

Status: DESIGN / NOT YET QUALIFIED
Branch: `dev-hub-v645-technology-truth-scoring-core-watch`

## Problem

Technology Watch is already mandatory, continuous, zero-spend-first and freshness-aware. That is not enough.

A fresh official announcement can still be technically misleading, incomplete, immature or unsafe. A newly released version can satisfy a claimed feature while introducing regressions. Multiple articles can repeat the same vendor claim and create false confidence. A product can also be genuinely capable but still be the wrong choice for ChaCha DEV.

V6.45 introduces evidence quality, adversarial verification and whole-core technology watch.

## Fundamental rule

**Recent is not true. Official is not proven. New is not automatically better.**

The preferred option is the best **verified-safe** option for ChaCha DEV, not automatically the newest version.

## Three independent scores

Technology Watch must never collapse all reasoning into one opaque number.

### 1. Technical Truth Score
Measures whether the claimed capability is actually demonstrated.

Evidence can include:
- executable reproduction / code / CI;
- official technical docs and exact release notes;
- reproducible benchmarks;
- issue trackers and maintainer discussions;
- independent technical blogs or postmortems;
- real pilot or project outcome evidence;
- security advisories and compatibility matrices.

Marketing or commercial claims can create a candidate, but cannot by themselves qualify it.

### 2. Operational Maturity Score
Measures whether the exact version is safe enough to use.

Signals include:
- exact release age;
- regression / bug velocity;
- unresolved high-impact issues;
- breaking changes;
- rollback path;
- compatibility with current runtime;
- security state;
- maintenance health;
- production/pilot evidence.

A technically true claim can therefore remain WATCH/PILOT if the version is too immature.

### 3. ChaCha DEV Architecture Fit Score
Measures whether the technology is actually appropriate for this platform.

Signals include:
- compatibility with current contracts;
- resource footprint;
- zero-spend / cost constraints;
- security boundaries;
- autonomy impact;
- observability;
- rollback complexity;
- foundry/agent integration impact;
- migration cost and blast radius.

A high Truth Score does not override poor Architecture Fit.

## Evidence hierarchy and independence

Evidence is version-bound and claim-bound.

Sources must be grouped by origin. Reposts, vendor syndication and articles repeating the same upstream source do not count as independent corroboration.

Strongest evidence is reproducible machine evidence. Independent technical evidence strengthens confidence. Official claims are useful but are never treated as independent confirmation of themselves.

Conflicting evidence lowers confidence and forces additional verification.

## Technology Watch ↔ Logician cooperation

Technology Watch owns the technology dossier and final technology evidence score.

Logician becomes its **falsification and verification strategy partner**.

For every material candidate, Technology Watch can ask Logician to produce:
- claims that must be falsified;
- counter-hypotheses;
- edge cases;
- regression paths;
- dependency and compatibility risks;
- missing evidence;
- candidate tests;
- cheapest/highest-value verification order;
- source-independence checks;
- alternative explanations for benchmark or vendor claims.

Logician must not select or promote the technology. It proposes how to challenge it.

Technology Watch executes or delegates the verification strategy and then recomputes scores.

Architecture Council remains final authority for architecture decisions.

## Hard gates

The following are non-negotiable:

- marketing-only evidence cannot produce ADOPT/ENABLED;
- an exact version must be identified for any version-sensitive recommendation;
- a core-platform upgrade cannot bypass executable regression evidence;
- a new or unstable version cannot be promoted only because it is newer;
- unresolved contradictory technical evidence blocks automatic adoption;
- critical security fixes may accelerate evaluation but do not remove rollback/test requirements;
- Technology Watch cannot grant production, network or secret permissions;
- automatic external spend remains 0 EUR without explicit human approval;
- Guardian and Sentinel authority remain preserved.

## Core Architecture Watch

Technology Watch must continuously cover the architecture of ChaCha DEV itself, not only technologies requested by projects.

Minimum core inventory:
- central brain / central orchestrator;
- Architecture Council;
- Logician and Ergonomist;
- Agent Foundry;
- Branch Foundry;
- Capability Foundry;
- specialist agents and dynamic agents;
- Guardian;
- Sentinel;
- Bastion;
- Intendant;
- assurance/external agents;
- Project Control / Verification Broker;
- scheduler / Run Controller;
- learning and memory fabric;
- reusable branch/architecture/capability registries;
- MCP/connectors/adapters/providers;
- VPS / NAS / Cloudflare execution surfaces;
- language/runtime dependencies such as Python and Node where platform-critical.

The watch must detect:
- deprecations;
- end-of-life;
- security advisories;
- breaking APIs;
- better verified alternatives;
- performance/resource improvements;
- pricing/quota changes;
- maintenance decline;
- architecture debt;
- unsupported versions.

It produces recommendations, not uncontrolled upgrades.

## Outcome feedback

Real project and pilot outcomes feed back into Technology Watch.

Repeated successful use strengthens exact technology/version confidence.
Verified regressions, rollbacks or incidents lower it.

Source reliability can also evolve:
- sources repeatedly confirmed by executable evidence gain reliability;
- sources repeatedly contradicted lose reliability;
- vendor marketing never becomes sufficient evidence by repetition.

## Explainability

Every recommendation must expose:
- exact technology and version;
- claims evaluated;
- supporting and contradicting evidence;
- evidence origins;
- independence groups;
- Truth Score;
- Maturity Score;
- Architecture Fit Score;
- unresolved uncertainties;
- Logician challenge summary;
- required next verification;
- rollback availability;
- final recommendation class and reason.

No opaque composite recommendation is allowed.

## Qualification targets

V6.45 qualification must prove at minimum:

1. official vendor claim alone cannot become ADOPT/ENABLED;
2. duplicated sources do not inflate evidence;
3. executable proof materially raises Truth Score;
4. exact-version maturity affects recommendation independently of truth;
5. contradictory evidence forces additional verification;
6. Logician produces falsification paths without owning the final decision;
7. Technology Watch can reject the newest version in favor of an older verified-safe version;
8. core ChaCha DEV components are present in the watch inventory;
9. verified pilot/project failures reduce technology confidence;
10. zero automatic external spend remains enforced;
11. Guardian/Sentinel/Architecture Council authority remains preserved;
12. V6.44 trust freshness and earlier acquired invariants remain regression-safe.

## Additional V6.45 mechanisms

### Publisher / source calibration
Technology Watch maintains a publisher confidence index learned from later verified outcomes. It is claim-class aware rather than a permanent reputation label. Confirmed executable outcomes increase confidence. Verified failures, attributed rollbacks and critical incidents reduce it. Marketing repetition never becomes technical proof merely because it is frequent.

### Evidence provenance graph
Each evaluated claim is connected to evidence nodes and independence groups. Reposts or syndicated copies sharing the same upstream origin are deduplicated. Supporting and contradicting edges remain visible.

### Adaptive proof with Logician
Logician ranks falsification experiments by expected information gain versus execution cost. The first test should be the one most likely to resolve the highest-risk uncertainty, not an arbitrary fixed checklist.

### Compatibility fingerprint and blast radius
Exact-version recommendations are evaluated against ChaCha DEV compatibility, security, resources, observability, rollback readiness, integration fit, cost fit and migration safety. High or critical blast-radius changes require stronger executable proof and SHADOW/PILOT evidence before ADOPT.

### Technology Debt Radar
The core watch maintains an explicit inventory of the ChaCha DEV nucleus and reports debt signals such as unsupported versions, EOL proximity, critical advisories, breaking APIs, maintenance decline and verified better alternatives. It recommends WATCH/PILOT/ACT states but never performs an uncontrolled core upgrade.

### Historical self-calibration
Technology Watch compares past confidence with real outcomes. Verified project/pilot failures lower technology confidence; repeated successful outcomes strengthen it. This creates a feedback loop for both technologies and information sources.
