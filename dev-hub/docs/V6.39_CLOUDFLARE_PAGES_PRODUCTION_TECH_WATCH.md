# ChaCha DEV V6.39 — Technology Watch: Cloudflare Pages production adapter

Date: 2026-09-23  
Status: DESIGN / QUALIFICATION ONLY  
Production mutation performed: NO

## Question

What is the narrowest zero-extra-cost production adapter suitable for the first
ChaCha DEV RELEASE -> OPERATE pilot for a static Golden Path application?

## Existing platform facts

The ChaCha DEV registry already contains:

- provider `cloudflare-pages`;
- adapter `cloudflare-pages-adapter`;
- status `ENABLED`;
- permission limited to `preview-deploy`.

V6.39 MUST NOT silently widen that preview adapter to production.

A distinct provider/adapter is therefore introduced:

- provider: `cloudflare-pages-production`;
- adapter: `cloudflare-pages-production-adapter`;
- initial status: `DESIGNED`;
- permissions: `read`, `production-deploy`;
- execution: VPS;
- executable: none until provisioning/promotion.

## Official Cloudflare findings

Sources checked on 2026-09-23:

1. Cloudflare Wrangler Pages commands  
   https://developers.cloudflare.com/workers/wrangler/commands/pages/

   Confirmed:
   - `wrangler pages deploy [DIRECTORY]`;
   - `--project-name`;
   - `--branch`;
   - `--commit-hash`;
   - `--commit-message`.

2. Cloudflare Pages Direct Upload  
   https://developers.cloudflare.com/pages/get-started/direct-upload/

   Confirmed that prebuilt assets can be deployed with Wrangler. Existing
   Git-integrated projects can also be deployed manually with Wrangler.

3. Cloudflare Pages deployments API  
   https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/

   Confirmed:
   - list deployments;
   - get deployment;
   - create deployment;
   - retry;
   - rollback.

4. Cloudflare Pages rollback API  
   https://developers.cloudflare.com/api/go/resources/pages/subresources/projects/subresources/deployments/methods/rollback/

   Confirmed:
   - POST rollback endpoint;
   - rollback target must be a successful production deployment;
   - Pages Write permission is required.

5. Cloudflare Pages project model  
   https://developers.cloudflare.com/api/resources/pages/

   Confirmed:
   - `canonical_deployment` identifies the current production deployment;
   - `production_branch` is exposed on the project.

## Architecture decision

Use a dedicated Cloudflare Pages production adapter with the following contract:

1. exact RELEASE revision is pinned;
2. project name is explicitly allowlisted;
3. production branch is explicit;
4. build directory already exists and is immutable input to the adapter;
5. Project Control `production-deployment` approval receipt is mandatory;
6. a hard runtime execution switch is mandatory;
7. the current `canonical_deployment` is captured before deploy;
8. deploy uses a pinned Wrangler version and explicit argv, never shell interpolation;
9. after deploy, `canonical_deployment` must change to a successful deployment;
10. health is checked against an explicit HTTPS canonical URL;
11. rollback calls the official Pages rollback endpoint using the captured prior deployment;
12. post-rollback `canonical_deployment` must equal the captured prior deployment;
13. no project creation, Pages settings mutation, domain mutation, secret mutation,
    production data write or destructive migration is allowed;
14. automatic external spend remains 0 EUR.

## Rejected design

Do not add `production-deploy` directly to the existing
`cloudflare-pages-adapter` preview adapter.

Reason: it would widen an already-enabled adapter's authority without a fresh
production-specific contract, provisioning evidence, promotion and human
approval.

## Current V6.39 status

The production adapter is DESIGNED only.

Its real write actions remain fail-closed until all of the following exist:

- contract qualification;
- provisioning receipt;
- runtime pilot;
- repeatability evidence;
- provider health evidence;
- machine-readable rollback;
- explicit production-capable adapter promotion approval;
- explicit project deployment approval.

No real Pages production deployment is authorized by this document.
