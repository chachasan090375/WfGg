## Objective

V6.39 addresses the next lifecycle boundary already defined by ChaCha DEV:

`RELEASE -> OPERATE`

The goal is to turn an acquired RELEASE candidate into a controlled real production deployment, with explicit human authority before the first production mutation and fail-closed verification after deployment.

V6.39 is not allowed to weaken RELEASE, V6.37 seven-agent finalization, or V6.38 human approval.

## Required lifecycle evidence

The existing `RELEASE -> OPERATE` transition requires:

- `production-deployment-receipt`
- `post-deploy-smoke`
- `production-health`
- `observability-health`
- `post-release-signed-checkpoint`
- `post-release-anchor-quorum`

Required gates remain:

- `identity-security`
- `ci-cd-release`
- `observability`
- `reliability-resilience`

## V6.39 design invariants

1. **No production mutation before explicit human approval.**
2. The deployment target must be explicit and project-scoped.
3. The deploy action must be executed through a controlled adapter; the central brain must not mutate production directly.
4. The exact RELEASE revision must be pinned before deployment.
5. The first production write must produce an auditable deployment transaction.
6. Post-deploy smoke and health checks must use the deployed target, not a local preview.
7. Observability must be proven from the real production target.
8. Any failed post-deploy gate triggers controlled rollback or containment; it must never be converted into a fake PASS.
9. Bastion retains emergency containment/quarantine authority and Emergency Stop stays out-of-band.
10. Guardian/Sentinel/Curator/Bastion/Intendant remain independent external authorities.
11. Architecture Council remains final for ordinary architecture changes.
12. Technology Watch remains mandatory for new deployment architecture.
13. Automatic external spend remains `0 EUR`; any paid solution requires explicit human approval.
14. RELEASE and OPERATE remain distinct states.
15. A successful production deployment is not enough by itself: OPERATE is reached only after all required evidence and gates are verified transactionally.
16. Rollback must be proven, not merely documented.
17. No secret may be embedded into client-side artifacts.
18. No direct Evidence Ledger or lifecycle mutation by the deployment controller.

Candidate approval id:

## Proposed real PILOT

The V6.39 real PILOT should:

1. start from an already RELEASED project;
2. prove the exact RELEASE revision and integrity;
3. resolve one explicit production target;
4. stop at `AWAITING_DEPLOYMENT_APPROVAL` before any production mutation;
5. resume only after explicit human approval;
6. deploy through the controlled adapter;
7. collect real production deployment receipt;
8. run real post-deploy smoke;
9. prove production health and observability health;
10. create a signed post-release checkpoint and trust-anchor quorum;
11. advance `RELEASE -> OPERATE` only through Project Control;
12. prove rollback/containment behavior;
13. finish with a dedicated `CHACHA_DEV_V639_INSTALL=PASS` marker.

Until that terminal marker exists in a real pilot, V6.39 remains NOT ACQUIRED.

## Out of scope for the first V6.39 pilot

- multi-region active/passive HA;
- automatic paid infrastructure expansion;
- blind replication of potentially compromised state;
- universal production adapters for every hosting provider;
- removal of the human production boundary.

The first pilot should use one narrow, explicit, reversible deployment profile.
